## 复用设计：精判 LLM 合并方案（LLM 调用次数审计）

### 背景
用户提出：精判复用不需要单独调一次 LLM，应该并入现有某次调用。随后要求列出改完后一轮对话的完整 LLM 调用清单。

### 代码确认结果
- coordinator.execute() 主链路完整 LLM 调用点：
  1. decompose（request_bundle.py:319, stage=request_bundle_decomposition）— 拆 RequestBundle
  2. entity extraction（coordinator.py:294, stage=graph_entity_candidate_extraction）— 提取金融实体
  3. need contract（planner.py:167, stage=upfront_request_need_planning）— 翻译为 Need 合约
  4. select worker（planner.py:501, stage=upfront_worker_call_selection）— 选 Worker
  5. specialist workers（N 次，_run_dag 内执行）— 各 Worker 执行
  6. Reporting Worker（_build_bundle_report_task → _run_dag，W06）— 组织最终回答

### 决策：精判复用合并进 #4 select worker
- 精判复用不再单独调 LLM，合并进 `_select_worker_calls`（#4）
- #4 的 prompt 在现有"选 Worker"指令基础上，追加复用候选和判定指令
- LLM 对每个 Need 先判"能否复用旧回答"，能 → 标 satisfied 不选 Worker，不能 → 照常选 Worker
- 改后 LLM 调用次数不变，只是 #4 prompt 更丰富

### 改后一轮对话 LLM 调用清单（单个 READ 请求）
- #1 decompose — 拆请求 + 粗筛复用（填 reuse_reference）
- #2 entity extraction — 提取金融实体
- #3 need contract — 翻译为 Need 合约
- #4 select worker — 选 Worker + 精判复用（确认 reuse/reject）
- #5..#5+N specialist workers — 执行（N = 未复用的 Need 数）
- #6 Reporting — 组织最终回答
- 总计 = 4 + N + 1 = N + 5 次
- 全部复用时 N=0，最少 5 次；无复用时 N=Need 数

### 复用逻辑分布在两次现有 LLM 调用中
- #1 decompose：看 ConversationInventory 摘要 → 粗筛，填 reuse_reference（候选标记）
- #4 select worker：看候选完整回答 → 精判，确认 reuse 或 reject + 选 Worker
- 两次都不新增独立调用，复用逻辑是"嵌入"式的

## 后续演进：调用链进一步压缩（用户二次优化）

### 用户提案
1. 实体提取（#2）是否必要？能否合并？
2. need 合约（#3）与选 worker（#4）合并为一次调用——"生成 need 的时候要看到 worker"

### 代码确认
- `_extract_mentions`（coordinator.py:272）内部已有词典层：`identity.extract_candidate_mentions` 先出 lexical_candidates（纯代码），LLM 只做过滤+角色标注（focus/comparison/cause/impact_target/context/event），随后 `identity.resolve_request` 确定性图解析成 GraphRef
- LLM 调用本身很轻：disable_thinking=True，max_output_tokens=500

### 依赖关系结论（关键约束）
- 图解析产出的 focus_refs 是 need 合约 LLM 的**输入** → 实体提取只能**往前并入 decompose**，不能往后并入 need 合约（同一次调用无法自产输入）
- 词典候选为空 且 entity_scope ∈ none/portfolio/account/global 时可跳过 LLM（安全降级：焦点落到 typed_focus/继承/SufficiencyGate）

### 最终决策
1. **实体提取**：先做条件触发（词典空+无实体 scope → 跳过 LLM），后做并入 decompose（RequestItem 增 mentions 字段）
2. **need 合约 + 选 worker + 精判复用 三合一**：用户指出现有缺口——need 生成不看 worker 名册，可能产出无 worker 能覆盖的 need。合并为 PlannerMergeCall，一次输出三段：needs / reuse_decisions / worker_calls
3. 三条守住：分段校验（needs 段合约形状 / reuse 段引用真实 / worker_calls 段覆盖性——每个 need 要么复用要么被覆盖，不允许悬空）；确定性编译不变（_generate_worker_dag/_compile 纯代码）；prompt 预算监控（worker 目录+候选回答）
4. 最终调用链：#1 decompose（含粗筛，可选吸收实体提取）→ 实体提取（条件触发）→ #2 合并规划 → #3..N 执行 workers → Reporting。固定 3 次 + N 次执行，对比现状 4 次固定，每轮至少省一次

## 架构定稿：两次调用版（用户三次收敛，最终形态）

### 用户定稿提案（纯设计，非现状）
- 第一次调用 decompose：生成 RequestBundle + 候选轮次编号（reuse_reference）；实体提取并入（RequestItem 增 mentions 字段，词典层调用前跑）
- 规则层：图解析（mentions → focus_refs）+ 候选筛选（轮次级保护过滤 / 去重 / 截断 ≤3 条，取完整回答裁剪版）
- 第二次调用合并规划：筛选后候选 + worker descriptions → 生成 needs，**每个 need 生成时就声明 binding**（worker_binding 或 reuse_binding 二选一）
- 规则层 2：DAG 编译（worker+参数相同的 need 绑定去重合并为一个节点；reuse 的 need 生成静态节点）
- 固定 LLM 调用：2 次 + 执行 N 次 + Reporting 1 次

### 逻辑检查三个硬点
1. N:1 映射丢失：need 级 worker 绑定会让同参数调用重复 → 规则层 2 按 (worker_id, call_args) 确定性去重合并
2. 覆盖性硬校验：每个 need 的 binding 二选一必填（悬空拒）；reuse_binding 引用必须在注入候选内；latest 意图下禁止 reuse_binding
3. reuse_binding 的 promised_data 只能来自候选 artifact_outputs——纯文本回答只能作 Reporting 参考输入（"回答级判断 + artifact 级注入"原则落地）

### 候选引用粒度澄清
- reuse_reference 引用的是轮次编号 turn_id，不是 conversation_id；一个会话多轮可复用回答各自成候选

## 设计修订：去重范围澄清 + 删除"产出名匹配"校验（用户质疑后收敛）

### 1. 去重对象澄清
- need 是意图单元（一个分析方向），worker 调用是计算单元——两者不同层面
- 同一份数据喂给两个不同方向的 need（如"分析上涨原因"+"评估风险"）→ 本来就不去重，各自执行
- 去重只针对极端情况：两个 need 绑定同一 worker + 同一参数（完全相同的计算）→ DAG 编译合并为一个节点
- 该去重是可选性能优化而非正确性规则，不做也不会错，只是重复计算

### 2. 删除"reuse_binding 产出名必须来自候选 artifact_outputs"校验
- 原意：防 LLM 只看摘要、声明不存在的产出（幻觉防护）
- 用户指出违背核心分工："让 LLM 写产出名 = 让 LLM 声明事实"，产出名是事实，只有共享存储知道
- 修订版：reuse_binding 只需 turn_id（+可选派生参数）；产出名由规则层从共享存储读取实际输出时注册，LLM 不碰
- 校验降级为存在性检查：turn_id 有货 → 注入；没货 → 该 need 回退 worker_binding 重算（与 latest 禁复用共用回退路径）

### 3. 理念基线（后续所有修改必须在此框架内）
- LLM 只判断意图（复用哪个轮次/选哪个 worker/参数派生方向），代码管事实（数据内容、结构、产出名、存在性）
- worker 输出放共享存储：生产者写入，消费者自取，无中间指名
- 回答永远重组：复用只省"算"不省"说"
- 硬校验收敛为两条：need 的 binding 二选一必填；latest 意图禁复用
